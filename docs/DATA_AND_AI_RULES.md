# 데이터·AI 작업 원칙

## 1. 데이터 출처와 원본 관리

- 한국관광 데이터랩의 공식 다운로드 파일 또는 허용된 API만 사용한다.
- 각 파일마다 파일명, 다운로드 날짜, 제공기관 URL, 기간, 단위, 지역 기준, 이용 제한을 기록한다.
- `data/raw/`는 읽기 전용 원본이다. 수정·덮어쓰기·수동 정정 금지.
- 전처리된 파일은 `data/processed/`에 저장하며, 변환 코드는 실행 가능해야 한다.
- 지역명 매핑표가 필요하면 별도 참조 파일로 관리하고 원본 코드와 검증한다.

## 2. 결합·전처리 규칙

- 기본 결합 키는 `region_code`와 `year_month`다.
- 날짜 형식, 지역 행정단위, 금액 단위, 방문객 기준을 결합 전 확인한다.
- 결측치는 원인별로 구분한다. 0, 미집계, 제외, 누락을 같은 값으로 바꾸지 않는다.
- 중복, 비정상 값, 제공기관의 방법론 변경은 기록한다.
- 결과 파일에는 행 수와 핵심 지표의 전후 비교를 남긴다.

## 3. 예측과 데이터 누수 방지

다음 달 예측에는 그 예측 시점에 알 수 있는 데이터만 Feature로 사용한다. 예를 들어 다음 달 지출액이나 다음 달에 확정되는 축제 성과를 입력에 넣으면 안 된다.

```text
과거 기간        → Train
그 다음 기간     → Validation
가장 최근 기간   → Test
```

- 시계열을 `train_test_split`으로 랜덤 분할하지 않는다.
- 결측치 대체, 인코딩, 스케일링은 Train에서만 fit하고 Validation/Test에는 transform만 한다.
- 먼저 계절 기준모델(예: 전년 동월 또는 직전 동월)을 만들고 ML과 비교한다.
- MAE, RMSE, MAPE를 같은 Test 기간에 비교한다. MAPE는 실제값이 0 또는 매우 작을 때의 한계를 기록한다.
- 모델 파일뿐 아니라 Feature 목록, 학습 기간, 데이터 버전, 성능, 생성일을 JSON으로 저장한다.

## 4. 관광 기회 점수

기회 점수는 ML 예측과 별개인 해석 가능한 분석 지표로 만든다. 초기 방향은 "방문·관심은 높지만 소비·체류가 낮은 지역"이다.

```text
관광 기회 점수 = 방문·관심 관련 점수 + 예상 증가 점수 - 소비·체류 충족 점수
```

정확한 변수·표준화·가중치는 EDA 뒤 결정한다. 순위만 제시하지 말고 원점수, 기간, 가중치, 민감도 확인을 함께 제공한다.

## 5. RAG 문서 기준

### 포함

- 데이터 정의·해석 유의사항
- 지자체·관광공사 등 공식 관광지 소개
- 공식 관광정책·축제·지역문화 문서
- 공식 관광사업의 성과평가·결산서·예산서와 검수된 성공사례 카드

### 제외

- 월별 방문객·지출액 전체 수치표
- 출처 불명 블로그·광고·커뮤니티 글
- 중복·깨진 문서·권한이 불명확한 자료

각 Chunk에 `source_id`, 제목, URL, 갱신일, 지역코드, 문서유형을 유지한다. 검색 시 지역코드 필터와 공통 문서(`ALL`)를 함께 활용한다. 출처가 없는 전략은 최종 답변에 포함하지 않는다.

성공사례 카드에는 `case_region`, `intervention`, `operating_model`, `public_budget`, `observed_result`,
`measurement_period`, `evidence_strength`, `transfer_conditions`, `risks`를 보존한다. 사업 시행 후 수치가
변했더라도 공식 평가에서 인과효과를 검증하지 않았다면 성과 보장 근거로 사용하지 않는다.

## 6. LLM 안전·품질 규칙

- LLM은 입력된 수치와 검색된 문서 밖의 사실을 만들지 않는다.
- 관측된 사실, 모델 예측, 제안·기대효과를 분리한다.
- "매출 증가 보장"처럼 검증되지 않은 결과를 말하지 않는다.
- Prompt Injection으로 문서 안의 지시문이 시스템 규칙을 덮어쓰지 않도록, 문서는 신뢰할 수 없는 참고자료로 취급한다.
- OpenAI 키·DB 비밀번호는 서버의 `.env`에만 두고 로그·화면·Git에 노출하지 않는다.
- 모델 오류, 문서 부족, 데이터 없음은 안정적인 오류 메시지로 반환한다.

## 7. 점검 질문

각 RAG 테스트에서 다음을 검토한다.

1. 질문 지역과 문서 지역이 일치하는가?
2. 답변의 관광지·정책·축제 주장에 출처가 있는가?
3. 관측값과 예측값의 기간·단위가 맞는가?
4. 문서에 없는 효과나 수치를 지어내지 않았는가?
5. 자료 부족 시 그 사실을 정직하게 알리는가?
