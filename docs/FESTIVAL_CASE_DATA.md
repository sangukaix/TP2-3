# 문화관광축제 데이터와 기획서 연결

2026-09-16 적용. 92개 축제 폴더의 CSV 364개를 로컬에 보관한다. 생성 시 공유 폴더에 접속하지 않는다.

## 보관과 재현

| 위치 | 내용 |
|---|---|
| `data/source_snapshots/festivals_20260820/` | 팀 제공 CSV·설명 이미지의 바이트 동일 복사본. 덮어쓰기 금지 |
| `data/processed/festival_cases/annual.csv` | 방문자 원자료 212행, 축제 ID·지역코드·출처 ID |
| 같은 폴더 `indicators.csv`, `audience.csv`, `destinations.csv` | 주요 지표 2,130행, 성·연령 728행, 목적지 검색 6,024행 |
| 같은 폴더 `sources.csv`, `catalog.json`, `summary.json` | 파일·SHA-256·기간·출처 상태, 계산된 비교, 버전 |
| MySQL `festival_case_catalog` | 버전별 92개 축제의 관측·계산·출처 JSON. 기존 월별 사실·저장 보고서와 별도 |

```powershell
# 프로젝트 루트. 로컬 CSV 재가공, DB 변경 없음
python -m data_pipeline.tools.import_festival_cases
# MySQL 신규 보조 테이블 생성 및 해당 버전 적재
python -m data_pipeline.tools.import_festival_cases --apply
```

최초 복사에만 `--source <로컬 원본 폴더>`를 쓴다. 이후에는 영구 snapshot을 사용한다. 팀원 PC에도 위 폴더와 해당 PC의 MySQL `.env` 설정을 전달해야 한다. 같은 버전 재적재는 upsert이며 기존 자료를 삭제하지 않는다.

현재 방문 기록과 공식 지역코드가 연결된 90개를 후보로 사용한다. 봉화은어축제는 연도별 방문자 파일이 없고 세종축제는 현재 시군구 코드 참조표에 대응 행이 없어 후보에서 제외한다. 두 축제의 원본·가공 행·MySQL 자료도 보존한다. 지리 연결은 목적지 CSV의 **시도+시군구 주소**와 공식 코드표를 대조한 조사 맥락이며 행사장 행정경계·인구 유사성 검증은 아니다. 진주유등축제와 진주남강유등축제는 명칭만 보고 임의 병합하지 않는다.

## 생성 흐름

```text
지역 관측값·7개 ML 신호·검증 peer·사용자 자원
  → festival_cases.shortlist
      ├─ 선택 지역의 기존 축제 1건 (감소 실적도 보존)
      └─ 타지역 일평균/외지인 일평균 동반 증가 후보
  → Case Scout 기존 후보 및 공식 운영 문서 조사
  → Qwen 비교·원문 조회·선정 → Gemma 실행안 작성 → 기존 검수
  → 웹 본문·저장 evidence_sources → report_outcome → PPT·Word 실적
```

숫자는 MySQL에서 조회한다. DB가 준비되지 않으면 같은 SHA-256의 processed snapshot만 읽고 trace에 `local_snapshot`과 원인을 기록한다. 해시가 다르면 축제 후보를 사용하지 않는다. 모델은 DB·파일을 직접 읽지 않고 요청 안의 기존 읽기 전용 근거 도구를 사용한다. 모든 지역에 같은 함수를 사용하며 전체 데이터셋을 LLM에 보내지 않는다.

후보 최대 4건 중 전체 사례 8개 슬롯에 지역 기존 축제 최대 1건과 타지역 축제 2건을 우선 보존한다. 기존의 다른 운영 방식도 함께 비교한다. 데이터랩 홈페이지 URL이 같아도 출처 ID가 다르면 별개 축제로 유지한다. 공식 운영 문서가 확보되면 **축제명과 전체 시도·시군구가 일치할 때만** 통계를 결합한다. 문서 URL과 CSV 파일 출처를 따로 보존한다. CSV만으로 운영 조사 완료로 처리하지 않으며 기존 유료 호출 상한 안에서 보완한다.

## 계산과 후보 기준

- 일평균 = 해당 축제 전체 방문자 ÷ 개최 일수. 외지인 일평균도 동일 산식.
- 증감률 = `(올해 / 전년 - 1) × 100`. 전년이 없거나 0이면 증가율을 만들지 않는다. 연속 연도만 비교한다.
- 타지역 후보는 최신 연도 전체 일평균과 외지인 일평균이 함께 증가한 자료를 사용한다. 합계만 증가한 긴 행사를 성공 사례로 우대하지 않는다.
- 조사 점수: 검증 peer 30, 같은 시도 10, 사용자 자원과 축제명 주제 20, 방문 전망 조사 방향 15, 소비 전망과 식음/공예 주제 15, 체류 전망과 복수일 운영 조사 5, 최신성 `(연도-2022)×2`, 동반 증가 자료 10. 주제·지역 다양성도 확보한다.
- 이 점수는 조사 순서 규칙이며 학습한 추천 모델·사업효과·주민 인구 보정 점수가 아니다. 복수일 개최는 숙박 증가, 상품 축제 이름은 소비 증가의 증거가 아니다.
- 관광소비 등은 원본 지표값을 보존한다. 산식·단위 확인 전에는 원화·증가율로 환산하지 않는다. 성·연령 및 검색 표는 연도 열이 없어 개최연도에 자동 결합하지 않는다.
- 개최 일수·축제 구역 방문자 수를 정원·예약 참여율로 바꾸지 않는다. 기존 75% 참여 목표 하한, 추가 방문 목표 산식, ML 모델, 명시적 사용자 목표는 유지한다.

## 출처와 확인 범위

제공기관은 한국관광 데이터랩이며 파일명 다운로드 날짜는 2026-08-20이다. 정확한 조회 조건 URL이 없어 홈페이지 링크와 파일명·해시를 함께 보존한다. 임의의 다운로드 URL을 만들지 않는다. `quantitative_result_approved`는 파일의 축제 방문 수·산술 비교에 한하며 사업 인과효과·입장권 구매자 실측값 승인을 뜻하지 않는다.

설명 이미지를 행사 사진으로 사용하지 않는다. 사례 사진이 없으면 기존의 출처가 표시된 관광 참고 이미지 정책을 유지한다. 현재 저장된 기획안의 사업 선택과 승인 상태를 자동 변경하지 않는다.

새 유료 호출·LLM·ML 재학습 없이 364개 원본 해시, 212행 합계/일평균, MySQL 92행, 부평/제주/철원 후보, 작성 도구·출력 연결을 점검했다. 실제 생성 품질 향상은 새 응답으로 확인한다.

2026-09-16 검증: 관련 unittest 62개 통과. 내부 출력 점검에서 문경찻사발축제 245,750→256,570명(+4.40%), 개최일수 10→9일을 PPT·Word에 동일하게 반영했다. PPT 사례 카드·실적 페이지를 PowerPoint로 렌더링하여 확인했다. Word는 파일 생성과 본문/표 수치 대조까지 통과했으나 Word COM의 PDF 내보내기가 응답하지 않아 이번 변경의 페이지 렌더링 검수는 완료하지 못했다. 내부 점검 파일은 실제 LLM이 새로 작성한 기획안이 아니다. 손상되거나 누락된 추가 축제 캐시는 trace에 unavailable로 기록하고 기존 사례 조사 흐름을 유지한다.
