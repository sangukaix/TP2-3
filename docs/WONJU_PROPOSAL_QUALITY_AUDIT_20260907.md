# 원주 기획안 품질 점검과 자료 요청 목록

점검 대상: 저장된 `원주 반값 여행 지역환급 모델 도입` 기획안. 저장 ID `0d6c8644149a48149b47da7250965fbc`.
범위: TP2-3만 수정. 기존 보고서·평가 점수·원자료·모델은 덮어쓰지 않음.
이 문서는 사업 승인서가 아니라 코드 점검 및 자료 보완 안내다.

## 1. 결론: 데이터가 전부 없는 문제가 아니다

실제 생성 기록에는 아래 근거 56건이 확보되어 있었다. **확보된 자료 수와 실제 기획에 인용·검증한 자료 수는 다르다.**

| 근거 종류 | 확보 건수 | 역할 |
|---|---:|---|
| 원주 월간 관측 출처 | 7 | 방문·소비·숙박·검색 등 지역 현황 |
| 전국 비교 출처 | 6 | 같은 정의·기간의 유사 지표 비교 |
| 전국 빅데이터 출처 | 12 | 전국/시군구의 보조 맥락 |
| 지역별 관광 현황 출처 | 3 | 유입·유출·인기 장소 등 |
| 저장 ML 예측 묶음 | 1 | 7개 대상 지표의 모델·예측·검증 기록 |
| 관광 Open API 자료 | 20 | 실제 관광자원·사진 등. 참여 협약 증명은 아님 |
| 최종 중복 제거 후 RAG 근거 | 1 | 공식 문서의 운영/해석 근거 |
| 공식 도메인 기반 검수 사례 카드 | 6 | 사업 운영 방식 비교. 일부 성과 수치 추가 검증 필요 |

Qwen3:14b가 적용성 검토·검수, Gemma4:26b가 초안·수정을 실행한 기록이 있다.
이 생성 건은 `student_budget`이며 무료 검색 키가 없어 새로운 무료 웹 검색은 하지 않았다.
로컬 품질 검수가 통과하지 않아 OpenAI 최종 검수도 실행하지 않았다. 이번 원인이 OpenAI 토큰 부족이나 개인 PC에 SQL이 없기 때문이라는 근거는 없다.

## 2. 실제로 잘못된 부분과 정비 내용

| 문제 | 원인 / 정비 |
|---|---|
| 후보가 2개인데도 후보가 부족하다고 반복 | 후보 수와 `selection_status=needs_evidence`를 같은 오류로 취급했다. 이제 후보 수 부족과 적용 조건 미확인을 구분한다. |
| 한 번 고쳤는데 후보 선정 상태는 그대로 | Gemma 본문 수정은 Qwen의 후보 JSON을 변경하지 못했다. 작성 가능한 후보 누락이 있으면 보유 근거로 Qwen 보완을 최대 1회 선행한다. |
| 후보가 원주에 왜 맞는지 모호 | 두 후보 모두 지역 적합성 출처가 다른 지역 사례 ID뿐이었다. 선택 지역 지표/검증 비교 출처와의 연결을 검사한다. |
| 전국 비교 지시가 로컬에는 빠짐 | OpenAI 장문 프롬프트와 로컬 전용 프롬프트가 달랐다. 전국 범위·인구 비교 한계·운영 차이 지시를 공유한다. |
| 예산에 항목만 있음 | '단가'라는 단어만 있어도 통과했다. 수량×단가 또는 명확한 곱셈 산식이 있어야 한다. |
| KPI 산식이 틀림 | `이번 값/전년 값`은 비율이지 증가율이 아니다. 증가율은 `(이번 값-전년 값)/전년 값×100`, 전년 0이면 계산 불가다. |
| 20%/5% 성공 기준이 갑자기 등장 | 출처·산출 근거 또는 잠정 가정 표시를 요구한다. 확정 효과처럼 쓰지 않는다. |
| 일정이 '모집/시스템 준비' 수준 | 단계별 담당 역할·입력 조건·실제 행동·산출물·미확보 시 대안을 쓰도록 강화한다. |
| 숫자를 확정할 수 없다는 이유로 감점 | 기획 전에는 사업의 순증 효과를 확정할 수 없다. 검수 지시를 산식/단위/측정 설계 점검으로 교정한다. |
| 상세 내용을 요구하면서 180자로 제한 | 비용·KPI·근거 필드의 획일적 180자 제한을 제거했다. 전체 출력 토큰 상한은 늘리지 않았다. |
| 작성/검수가 첫 사례만 읽음 | 실제 선택·추천 사례를 먼저 읽고 후보 비교 내용도 조회한다. 사전 원문 조회는 최대 3개로 제한하고 추가 인용은 기존 원문 검증 절차를 따른다. |
| 경고 일부만 화면에 표시 | 상위 5개만 보이던 제한을 없앴다. 전체 코드 점검과 '보완 방법·준비할 자료'를 표시한다. |

현재 표의 검사는 완전한 의미·인과 검증을 대신하지 않는다. 문장 안에 키워드가 있다는 사실만으로 실제 협약·성과가 입증되지는 않는다. 독립 검수와 담당자 확인은 유지한다.

### 강진의 46%는 어떻게 처리했나?

기존 카드의 [공식 도메인 소개 페이지](https://jnfarm.jeonnam.go.kr/board/FARM_BOARD_008/boardView.do?bdId=BD_00000000000011721&menuCd=farm004002)는 상품권 결제 증가를 소개하지만, 정확한 집계 범위·원자료·사업의 순증 효과를 입증하지 않는다. 게시일도 사업기간과 구분해야 한다.

- 과거 수치 문구는 레지스트리의 `historical_unverified_claim`에 감사용으로 보존했다.
- 생성용 카드에는 성과 수치 인용 보류(`quantitative_result_approved=false`)와 낮은 근거 강도를 표시했다.
- 게시일을 확인된 2025-01-02로 정정하고 2024년 사업기간과 분리했다.
- 같은 출처의 오래된 RAG 요약이 최신 교정 카드를 덮어쓰지 않게 했다.
- 이는 강진 사업 자체가 효과 없다는 판단이 아니다. 원주 효과의 정량 근거로 쓸 증거가 부족하다는 뜻이다.

## 3. 지금 준비해 주면 가장 도움이 되는 자료

**이미 보유한 전국 관광 원자료 전체를 다시 받을 필요는 없다. 아래 자료를 우선순위대로, 구할 수 있는 것부터 보내면 된다.**

### 우선 1 — 원주에서 상품권 환급 사업을 운영할 수 있는 조건

찾을 문서: 원주시 관광객 인센티브 지원 공고/운영지침, 원주사랑상품권 발행·운영 공고, 가맹점/정산 안내.

필요 항목:

- 관광객 환급을 상품권으로 지급할 수 있는지, 필요한 승인·운영 주체
- 외지인 자격, 개인/팀 신청 단위, 인정 업종, 가맹점 조건
- 최소 지출액, 환급률·상한을 정할 수 있는 범위, 지급 시점
- 취소·중복 수혜·부정 신청 처리, 운영/정산 수수료
- 익명 또는 집계자료 제공 가능 항목

형식: 공식 URL 또는 PDF/HWP. 공고가 없으면 담당 부서의 확인 가능 범위를 알려줘도 된다. 가맹점 안내만으로 신규 관광 환급 사업의 허용을 추정하지 않는다.

찾아둔 출발점: [원주시 상품권 안내](https://www.wonju.go.kr/www/contents.do?key=5984), [가맹점 신청 안내](https://www.wonju.go.kr/wonjusarang/user_sub.php?gid=www&mu_idx=9). 페이지의 구매 할인·가맹점 환전은 관광객 환급 사업과 구분해야 한다. 운영 시점의 최신 공고를 다시 확인한다.

### 우선 2 — 비교 사업의 공식 결과보고서 2~3종

가능하면 환급 외에 예약/체험 결합·이동 연계·재방문 등 다른 운영 원리도 포함한다. 강원도 사례만 고집하지 않고 전국에서 찾는다.

필요 항목:

- 사업명·지자체·운영기간·실제 참여 대상/건수
- 지원 방식, 신청/지급/재사용 절차, 참여업체 수
- 예산 총액·집행액·주요 비용 항목
- 성과 지표의 정의·비교기간·원자료·측정 방법
- 운영상 문제, 미사용/취소·민원, 사업 종료 후 유지 방식

추천 문서 유형: 공식 성과평가서, 결산서, 결과보고서, 입찰 과업지시서/계약 내역. 홍보 보도자료 한 장보다 운영 조건과 측정 정의가 중요하다.

강진은 [현재 운영 신청 안내](https://www.gangjintour.com/advance/advance_req.html)에서 제도 방식을 참고할 수 있으나, 현재 조건을 2024년 실적에 소급하지 않는다. 디지털 관광주민증/교통 할인은 원주 참여 자격과 협약을 별도로 확인해야 한다.

### 우선 3 — 참고 견적을 현실적으로 만드는 자료

지금 금액을 모르면 미정으로 둘 수 있다. 아래 중 확보 가능한 것을 보내면 된다.

- 희망 총예산 또는 최대 상한, 희망 운영기간, 담당 인력
- 인력/정산 대행/기존 시스템 이용/홍보/평가의 견적 또는 공공 계약 내역
- 수량, 단가, 금액 단위, 부가세 포함 여부, 기준일
- 대상 업체·운영일수·지급 건수는 확정치와 가정을 구분

공식 단가가 없으면 기획 가정으로 임시 견적을 만들 수 있지만, **확정 견적은 아니라고 표시**한다. 새 앱·키오스크 구축비를 기존 도구 이용료에 포함한 것처럼 쓰지 않는다.

### 우선 4 — 실제 추가 소비 효과를 검증할 집계자료

있으면 좋고, 신규 사업의 사후 실적은 지금 존재하지 않아도 된다. 사전에는 수집 가능 여부와 설계부터 정한다.

기준기간: 계획한 운영 월의 전년 동기 + 직전 기준기간. 같은 가맹점/업종/환불 처리 범위를 맞춘다.
예: 2026년 10~11월 운영이면 2025년 10~11월 비교자료와 2026년 사전 기준기간을 검토한다. 특정 날짜를 모든 지역의 고정값으로 쓰지 않는다.

가능한 집계표 열:

```text
기준일/월 | 지역코드 | 대상 권역/업종 | 집계 대상 정의
신청 건수 | 적격 건수 | 지급 건수 | 지급액
취소 제외 인정 소비액 | 상품권 재사용액/건수
비교집단 구분 | 수집기관 | 원자료 설명
```

원주 전체 관광소비와 이 사업 참여자의 소비를 혼합하지 않는다. 재사용액은 기존 지출 대체일 수 있으므로 전부 순증 소비로 간주하지 않는다. 비교집단이 없으면 인과효과가 아닌 운영 실적으로 보고한다.

**이름·전화번호·주민등록번호·카드번호·개인별 이동기록은 보내지 말고 익명 집계만 제공한다.**

### 선택 — 최신 월 데이터와 인구 비교

- 이번 저장안의 원주 ML 학습자료는 2024-01~2026-06이다. 공식 7~8월 자료를 내려받을 수 있으면 업데이트에 도움이 된다. 3개월 이상 공백 차단 정책은 유지한다.
- '인구 규모가 유사한 지역'이라는 비교가 꼭 필요하면 시군구 코드·기준월이 있는 공식 주민등록 인구표를 제공한다. 현재 유사 지역은 방문·소비·숙박 지표 기준이지 인구 기준이 아니다.
- 무료 검색 키 설정은 선택 사항이다. 키를 채팅으로 보내지 않는다. 공식 URL/PDF 제공으로도 문서 근거를 보강할 수 있다.

## 4. 원주 기획안에서 지켜야 할 계산 구분

```text
ML 자연추세          = 과거 관측으로 예측한 방문/소비, 사업효과 아님
환급 공공비용        = 각 적격 신청 min(인정 지출×가정 환급률, 상한)의 합
운영 목표            = 예산·용량에 맞춘 신청/지급/재사용 목표안, 가정 표시
전년 대비 결제 증가율 = (이번 값-전년 값)/전년 값×100, 전년 0이면 계산 불가
사업으로 늘어난 소비 = 별도 비교 설계·원자료로 평가, 전후 차이만으로 확정 불가
```

현재 저장된 원주 방문·소비 모델은 시험 MAE가 계절 기준선보다 크다. 실제 저장 예측을 보여주되 정확도가 우수하다거나 이 예측으로 사업 효과가 보장된다고 쓰지 않는다. 데이터의 추가 수집과 시계열 재검증이 필요하며 이번 작업에서 임의로 모델을 바꾸지는 않았다.

## 5. 수정 후 생성 흐름

```text
관측·SQL·저장 ML + 공식 사례·RAG
  → 전국 범위 사례 후보 정리(같은 시도 + 타시도 peer + 운영 방식)
  → Qwen 적용성·후보 비교
  → 후보 계약 검사
      ├ 작성 가능한 누락: 보유 자료로 Qwen 보완 최대 1회
      └ 실제 근거 미확인: 조건·자료 필요 표시 유지
  → Gemma 본문 작성
  → 코드 점검 + Qwen 검수
  → 필요 시 Gemma 본문 수정 1회 + Qwen 재검수
  → 로컬 통과본만 기존 정책에 따라 OpenAI 독립 최종 검수 1회
  → 초안 보존 + 전체 점검 결과 + 준비할 자료 목록
```

학생 절약 모드의 유료 호출 상한은 늘리지 않았다. 새 사업을 만들 때 원주뿐 아니라 모든 지역에 같은 계약이 적용된다. 기존 저장 기획안이 이 코드 변경만으로 자동 수정되지는 않는다.

## 6. 검증과 남은 한계

- 2026-09-07 후속 점검에서 PDF의 서로 다른 페이지 청크가 같은 `source_id`라는 이유로 덮어써질 수 있는 경로를 수정했다. 이제 `(source_id, chunk_id)`별로 보존하고, 로컬 Agent가 PDF를 인용하려면 모든 반환 청크를 순서대로 읽어야 한다. 이 수정 전 생성된 보고서의 RAG 1건 표시는 해당 손실 가능성이 있었으므로, 새로 생성할 때 다시 확인해야 한다.
- 실모델 단축 점검은 2026-09-07에 Qwen 3 14B와 Gemma 4 26B에서 모두 통과했다. 두 모델 모두 합성 근거의 마지막 예측월, 수치, 단위, 비교 방향, `policy_effect_proven=false`, 실제 사례 ID를 JSON으로 정확히 반환했다. 이는 연결·Schema 의미 전달 확인일 뿐, 전체 지역 기획안의 품질 승인이나 사업 효과 검증은 아니다.
- 공식 PDF 지표 정의를 보강하기 위해 데이터 세미나 PDF 76쪽을 화면 검수했다. 이동통신·신용카드·숙박예약·인허가 데이터의 대상·기간이 다름을 명시한 요약만 RAG에 추가했다. 75~99쪽 중 23쪽은 특수 폰트/이미지로 텍스트 추출이 되지 않아 자동 색인하지 않았다. 지방공항 PDF 34~44쪽은 추출 가능했다.

- 관련 회귀 테스트 및 프론트엔드 lint/build를 실행했다. 상세 결과는 작업 완료 메시지를 참조한다.
- 관련 회귀 테스트는 후속 PDF·청크 보존 및 미래 월 누수 검사를 포함한 선택 171개가 통과했다. 프론트엔드 lint는 오류 없이 기존 Hook 경고 2개, build는 성공했다. 테스트에서 의도한 잘못된 PDF·저장 실패 경로 로그는 실제 생성 실패 기록이 아니다.
- 실제 원주 snapshot을 읽어 전국 비교·전국 빅데이터 MySQL 맥락이 모두 사용 가능한 상태임을 확인했다. 기존 보고서를 새 규칙으로 점검하면 16건이 검출되며, 새 보완 안내 필드의 응답 직렬화도 통과했다. 원래 저장안은 수정하지 않았다.
- 반복되는 표의 열 이름을 한 번만 전달하는 무손실 표 형식(`context_tables.py`)과 동일 관측/선택 후보의 중복 전달 제거를 적용했다. 표를 복원한 모든 수치·문자열·null·출처가 원본과 동일함을 검증했다. 원자료·도구 저장소는 그대로 유지한다.
- 원주 실제 근거 묶음의 보수적 입력 추정/출력 예약은 적용성 25,737/5,600, 초안 23,998/16,000, 수정 26,070/14,000, 검수 25,104/5,500 토큰이었다. 모두 40,960 문맥 사전검사를 통과했다. **실제 모델 토큰 사용량이 아닌 오프라인 추정치**이며 추가 조회·다른 지역·더 긴 초안은 여전히 초과할 수 있다. 이때 근거를 자르거나 상한을 우회하지 않는다.
- 검사 규칙은 출처 연결·형식·누락·일부 명확한 산식 오류를 잡는다. 사업의 인과효과·계약 허용 여부를 자동 증명하는 도구는 아니다.
- 초기 개인 노트북 Ollama 조회는 시간 초과였지만, 2026-09-07 재조회에서는 `qwen3:14b`와 `gemma4:26b` 목록을 확인했다. 전체 실제 기획 생성의 품질 통과와 모델 목록 연결 성공은 별개다. 실모델 단축 점검 결과는 아래 검증 기록을 따른다.
- 프로젝트 유료 OpenAI 생성/임베딩을 이 점검 때문에 호출하지 않았다. 수정된 모델 가중치도 없다. 변경 대상은 도구 전달·작성 지시·검증 및 보완 흐름이다.
- 작성 지시 정비는 명시적인 역할/제약/출력 계약과 검증을 권하는 [OpenAI 공식 프롬프트 안내](https://developers.openai.com/api/docs/guides/prompt-engineering)를 참고했다. 공식 문서가 관광사업 효과를 보증하는 것은 아니다.
