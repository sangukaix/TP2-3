## 무엇이 잘못 연결되었나

춘천의 지역상품권 환급 프로그램에 Qwen이 `case:jeonju_night_budget_2026`을 대표 사례로 연결했다. 해당 문서는 야간관광 사업의 예산 항목을 보여 줄 뿐 환급 운영이나 방문·소비 증가를 증명하지 않는다. 문서 등급 high는 출처 신뢰도이며 해당 사업과의 적합성 점수가 아니다. 이 구분이 최종 사례 연결에 강제되지 않았다.

## 추천 알고리즘은 무엇인가

기존의 **통계적 비교 지역**과 **참고 사업 선택**은 서로 다른 경로다.

1. `data_pipeline/tools/build_planning_context.py::build_peer_rows`는 같은 기간의 관측값으로 지역 프로필을 만든다. 12개월 방문 수의 log1p, 소비액/방문 수 비율, 숙박 방문 비율, 평균 숙박일수를 사용한다. 각 열을 `(값−평균)/표준편차`로 표준화하고, 네 변수의 유클리드 거리 `sqrt(sum((z대상−z비교)^2))`가 작은 5곳을 고른다. MySQL `regional_peer_comparison`에 저장하고 `nationwide_context_store.py`가 읽는다. 이는 7개 미래 예측값을 학습한 사업 추천 모델이 아니며, 인구·해안/내륙·산악·교통을 포함한 환경 유사성을 입증하지 않는다.
2. `case_scope.py::select_case_cards`는 소재지 범위, 공식 문서 등급, 서로 다른 운영 방식이 후보군에 포함되도록 정렬한다. 자료 수집용 순서이며 성공 확률이 아니다.
3. 기존에는 `TransferabilityAgent.assess`의 Qwen이 사례 연결·fit_score·설계 후보를 작성하고 Gemma가 본문을 작성했다. Qwen이 별도 ML 추천 모델을 훈련한 것은 아니다. 프롬프트의 판단 기준에 따라 텍스트와 JSON을 생성했다.
4. 이번 변경은 `case_recommendation.py`의 명시적 함수 규칙이다. 예산 문서를 운영 후보에서 제외 → 공식 URL과 운영 설명이 있는 사례만 사용 → 실제 사업 방식(환급·숙박·야간 등)을 분류 → 같은 방식만 연결 → 문서 등급과 ID로 동률 정렬한다. 근거가 없으면 연결 ID는 빈 목록이다. 문서 검토를 대체하는 의미 이해 모델이 아니며, 키워드 분류의 한계는 남는다.

`TransferabilityAgent`의 입력과 응답 양쪽에 이 규칙을 적용한다. 화면·문서용 `prepare_idea_report`에도 적용하여 기존 저장 보고서를 다시 내보낼 때 같은 오류가 반복되지 않게 했다. 원래 연결·문구·평가 점수는 감사 필드에 남긴다. 생성 호출 횟수나 승인 상태는 늘리거나 변경하지 않는다.

춘천 출력에서는 환급 방식에 일치하는 강진을 핵심 운영 참고로 연결한다. 인천의 숙박·식사·체험 묶음과 디지털 관광주민증은 다른 운영 방식을 비교하는 카드다. 이 세 곳을 춘천과 환경적으로 유사한 지역이라고 부르지 않는다.

## 전주 예산서와 다른 문서는 어디서 왔나

- 전주 예산서는 `data/rag/official_case_studies.jsonl`에 등록된 검수 카드다. `_load_curated_case_cards`가 파일을 읽고, 같은 URL의 중복 자료는 먼저 등록된 카드가 유지된다. 따라서 이 저장 보고서의 대표 전주 카드는 새 웹 검색이나 임베딩 순위가 만든 자료로 설명하면 안 된다.
- 당시 trace에는 `curated_registry`, `case_rag`, `official_case_web`, `national_case_selection`이 함께 있다. 웹 조사 실행 사실만으로 각 출처가 웹 검색에서 새로 발견됐다고 단정할 수 없다.
- 저장된 지방공항 정책 문서는 `retrieval_method=local_curated_chunk`였다. 모든 문서를 Chroma 의미 검색으로 가져왔다고 설명하지 않는다.
- 앞으로 사례 출처 레코드에는 `retrieval_method`, `document_type`, `retrieval_context`, 측정기간·실적·적용 조건을 함께 전달한다. 검수 파일은 `curated_registry`, 새 웹 카드는 `official_web_search`로 구분한다.

## KPI는 무엇을 근거로 하나

공식 확인: [강진군의회 2024-11-20 시정연설](https://clik.nanet.go.kr/minutes/viewer.do?DOCID=CLIKC3524169218564260&collection=minutes)은 10월 말 방문 약 248만 명, 전년 대비 25% 증가를 발표했다. 역산 비교 규모는 `248만/1.25=198.4만`, 차이는 `49.6만`이다. 이 두 값은 별도 원자료가 아닌 역산값이다.

시정연설은 반값여행과 축제가 함께 운영된 기간의 전체 변화를 설명한다. 사업 단독 인과효과, ML 전망 대비 증가, 8·9·10월의 동일 기준 전후 소비액은 여기서 얻을 수 없다. 25%의 1/5인 5%는 작은 시범사업의 조정 가능한 계획 판단이며 통계적으로 추정한 계수가 아니다. 인구 보정 계수도 적용하지 않았다. 사용자 지정 목표는 유지한다.

7개 ML 모듈은 자연추세를 제공한다. 월별 방문 목표는 `ML방문×(1+최종월 목표율×경과월/전체월)`이다. 방문·소비 목표율이 같을 때 소비 목표는 `ML소비+(목표방문−ML방문)×(ML소비/ML방문)`이다. 그러므로 월별 두 증가율은 같다. 소비/방문 비율은 기획용 지표이며 서로 다른 데이터 모집단을 결합한 실제 개인 객단가가 아니다.

현재 1,000건 지원 예산으로 추가 방문 20만 명 전체가 발생한다고 입증할 수 없다. 도시 전체 목표와 운영 예산은 각각의 계획 가정이다. 실측 정책 효과로 연결하려면 참여·미참여 집단, 동일 기간과 집계 기준을 갖춘 평가 자료가 필요하다.

## 실행 01~04는 어디서 만들어졌나

`proposal_layout_v9.py::execution_groups`는 저장된 `implementation_steps`의 일정을 네 단계로 묶는다. `execution_copy`는 환급형과 일반형 운영 안내를 코드에 정의한다. 현장 협약이나 공식 지침을 그대로 발췌한 문장이 아니고 웹 검색·ML 추천으로 매번 작성한 것도 아니다. 저장된 원래 업무와 산출물은 발표자 노트에 보존한다. 이번에는 두 장을 `4단계 실행 가이드 예시안` 한 장으로 합쳤다.

## 견적 8,250만 원은 어떻게 나오나

`proposal_evidence.py::build_reference_estimate`가 기간·환급 여부·예산 상한을 입력으로 계산한다. 3개월 환급형 예시는 다음과 같다.

| 항목 | 공식 | 포함 이유 |
|---|---|---|
| 환급 지원 | 1,000건 × 50,000원 = 5,000만 원 | 이용자 혜택 |
| 현장 운영·정산 | 월 20인일 × 3개월 × 150,000원 = 900만 원 | 접수·확인·안내·정산 |
| 신청·증빙 시스템 | 기존 수단 설정 1식 × 800만 원 | 신청·증빙 관리 |
| 홍보·참여처 안내 | 1식 × 500만 원 | 모집·사용 안내 |
| 성과 집계·검토 | 1식 × 300만 원 | 실적 정리 |
| 예비비 | 직접비 7,500만 원 × 10% = 750만 원 | 변경 비용 |

총액은 8,250만 원이다. 전 항목의 단가·수량은 기획용 코드 가정이며 공식 표준단가·실제 공급업체 견적·ML 예측이 아니다. 환급 여부는 혜택 항목을 바꾸고 기간은 건수와 인일을 바꾼다. 강진 신청 규칙 링크는 운영 방식의 참고이며 위 단가의 근거가 아니다. 사용자가 총액을 조정하면 `scale_estimate`가 비중 배분하고 기존 수량 공식을 제거한다.
