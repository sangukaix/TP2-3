# 의사결정 기록

아래의 확정된 결정은 임의로 바꾸지 않는다. 사용자가 승인한 새로운 결정은 같은 형식으로 추가한다.

## 확정

### D-034 강남구 수요 예측의 1차 ML 범위

- 날짜: 2026-08-28
- 상태: 승인됨
- 결정: 강남구 2024.01~2026.07 공식 월별 원자료로 다음 달 순 방문자 수와 외지인 관광소비액을 각각 예측한다. 최근 3개월 관측과 이후 3개월 예측을 지역선택 대시보드에 함께 표시한다.
- 이유: 원자료만 보여주는 화면을 넘어, 담당자가 단기 수요 흐름을 읽을 수 있게 하기 위함이다. 두 목표값의 검증 성능이 달라 단일 모델로 묶지 않는다.
- 결과: 학습은 `ai_server/ml`의 명시적 CLI에서만 수행하고, 저장 artifact만 API가 읽는다. 최근 4개월 시간순 테스트에서 seasonal-naive 기준선보다 MAE가 낮지 않으면 artifact를 저장하지 않는다. 업종별 소비 패턴은 최신 관측 비중을 적용한 가정이지 업종별 ML 결과가 아니다.

### D-001 서비스 방향

- 결정: 일반 여행자 챗봇이 아닌 관광정책·소상공인 전략 서비스
- 이유: 관광데이터랩 활용도와 지역 경제 효과를 더 분명히 보여 줄 수 있음

### D-002 AI 역할 분리

- 결정: ML은 수요 숫자 예측, MySQL은 정확한 수치 조회, RAG는 공식 문서 검색, LLM은 설명·전략 생성
- 이유: 환각을 낮추고 발표에서 각 기술의 역할이 분명함

### D-003 앱 구조

- 결정: React/Vite + FastAPI Backend + FastAPI AI Server + MySQL + ChromaDB + OpenAI API + Nginx + AWS EC2
- 이유: 강사 제공 구조와 맞고 AI 로직을 분리할 수 있음

### D-004 예측 과제

- 상태: 잠정
- 결정: 지역별 다음 달 방문객 수를 회귀로 예측
- 조건: 실제 데이터의 기간·일관성이 확인되어야 함

### D-005 벡터 DB

- 결정: MVP에는 영속형 ChromaDB 사용. Qdrant는 확장 단계에서만 검토

### D-006 Fine-tuning

- 결정: MVP에서는 하지 않음
- 이유: 변하는 공식 지식은 재임베딩 가능한 RAG가 적합하며, 숫자 근거 문제도 해결하지 못함

### D-007 강남구 단기 시연 대시보드

- 상태: 승인됨
- 결정: 최종 React/Vite MVP와 분리해, 강남구 2025-08~2026-07 데이터로 Streamlit 시연 화면을 만든다.
- 이유: 공무원 사용 관점의 대시보드와 AI 전략 보고서 흐름을 빠르게 검증하기 위해서다.
- 결과: 12개월 표본의 ML은 기준선·후보 모델을 보여 주는 교육용 시연으로만 사용하며, 정식 예측 성능이나 정책 판단 근거로 주장하지 않는다. OpenAI 키는 서버 측 `.env`에서만 읽는다.

### D-008 React/Vite UI 골격

- 상태: 승인됨
- 결정: `frontend/`에 React + Vite 기반의 시군구 관광 대시보드 UI를 먼저 만든다. 지도는 React Leaflet, 그래프는 Recharts를 사용하며, 시연 데이터는 `src/data/`에 격리한다.
- 이유: 실제 데이터셋이 취합되기 전에도 공무원 사용 흐름과 반응형 레이아웃을 검토할 수 있고, 이후 FastAPI `/api`, `/ai` 응답으로 안전하게 교체할 수 있다.
- 주의: 화면의 모든 수치·예측·전략 문구는 시연값임을 표시한다. 실제 시군구 경계는 검증된 GeoJSON과 지역코드가 준비된 뒤에 연결한다.

### D-009 시군구 경계 지도

- 상태: 승인됨
- 결정: VWorld WFS 행정구역 경계를 일반 FastAPI Backend가 서버 측에서 조회해 React에 GeoJSON으로 전달한다. React는 React Leaflet으로 면 경계를 표시하고, 키를 직접 읽지 않는다.
- 이유: 참고 화면과 같은 클릭형 시군구 지도를 만들면서 VWorld 인증키 노출을 막고, 지도 응답을 캐시해 외부 API 호출을 줄일 수 있다.
- 주의: VWorld 현행 코드와 과거 관광 원자료 코드는 다를 수 있다. 예를 들어 전북·강원의 변경 전 코드는 지역코드 매핑표 검증 전에는 직접 조인하지 않는다.

### D-010 2단계 지역 선택 지도

- 상태: 승인됨
- 결정: 전국 지도는 고정하고, `시도 선택 → 해당 시도의 시군구 선택` 순서의 두 선택창을 지도 위에 둔다. 시도는 청록색, 선택한 시군구는 주황색으로 같은 지도 위에 겹쳐 표시한다.
- 추가: 첫 화면 검색창에서 도·시·군·구 이름을 입력하면 같은 시도·시군구 선택 상태로 연결한다.
- 이유: 지자체 담당자가 본인 지역을 빠르게 찾되, 시군구 선택 때 전국 지도 위치·맥락이 바뀌지 않게 하기 위해서다.
- 주의: VWorld 현행 경계에서 광주·전남 통합처럼 행정구역이 변경된 경우에는 현재 공식 경계 기준을 표시한다. 데이터 원자료의 기준 시점과 다르면 매핑·표기 기준을 별도로 검증한다.

### D-011 강남구 OpenAI 전략 보고서 테스트

- 상태: 승인됨
- 결정: 강남구 원본 ZIP의 최신 방문·소비·체류·관심도 관측값을 별도 AI 서버가 읽고, OpenAI가 구조화된 종합 전략기획서를 생성한다. 보고서에는 원본 ZIP에서 재계산한 월간 방문·관광소비 그래프, 기간별 전략 로드맵, 담당자 목표 입력형 시나리오와 `다음 달`·`3개월 이내`·`1년 이내` 전략을 함께 표시한다.
- 이유: 공무원·소상공인용 핵심 흐름을 실제 데이터 기반으로 먼저 검증하기 위해서다.
- 주의: 12개월 표본이므로 예측 성능·정책 효과를 주장하지 않는다. 관측 사실과 AI 제안을 표기에서 분리한다. 시나리오의 소비 목표액은 사용자 입력 목표율을 최근 월 관측값에 단순 환산한 값이며 예측·인과효과가 아니다. 단가·견적·유사사업 예산의 공식 근거가 없으므로 AI가 예산 금액을 만들지 않으며, 예산 산정 필요 항목만 제시한다.
- 추가: `GET /ai/v1/demo/11680/dashboard`는 OpenAI를 호출하지 않고 강남구 ZIP에서 최신월·전월 대비 상단 카드 3개를 계산한다. 이 테스트 경로는 다른 지역의 데이터 검증과 MySQL 이전 전까지만 사용한다.

### D-012 담당자용 4단계 의사결정 UI

- 상태: 승인됨
- 결정: React 화면에 `지역 선택 → 전국 진단 → 지역 결과 → 정책 시뮬레이션` 탭 흐름을 둔다. 정책 시뮬레이션은 목표값을 조절하는 UI를 먼저 제공하며, 검증된 전국 비교·예측 모델이 연결되기 전에는 금액·순위·정책 효과를 사실처럼 표시하지 않는다.
- 이유: 담당자가 데이터 확인부터 실행 검토까지의 순서를 쉽게 이해하고, 향후 ML·MySQL·RAG 결과를 같은 화면에 연결할 수 있게 하기 위함이다.
- 주의: 시뮬레이션 결과는 가정 기반 시나리오이며 인과효과·매출 증가를 보장하지 않는다.

### D-013 데이터 출처·의존성 변경 기록

- 상태: 승인됨
- 결정: 데이터랩 ZIP은 월별 사실·전처리·ML의 중심 데이터로, 관광 Open API는 관광자원·인프라·공식 맥락을 보강하는 데이터로 역할을 분리한다. 실제 연결 상태는 `docs/DATA_SOURCE_USAGE.md`에서 관리한다.
- 이유: 화면의 수치가 어떤 원본에서 나왔는지, 어떤 Open API가 실제 사용 중인지 팀원이 같은 기준으로 확인하기 위해서다.
- 결과: 새 ZIP 또는 API를 실제 화면·분석·보고서에 연결할 때 출처 문서와 필요한 의존성 파일(`requirements.txt` 또는 `frontend/package.json`)을 같은 변경에서 갱신한다. API 키는 서버 `.env`에만 보관한다.

### D-014 AI 전략 화면과 Word 기획서 분리

- 상태: 승인됨
- 결정: 화면의 AI 리포트는 핵심 요약, 원자료 월간 변화, 기간별 실행 전략, 담당자 입력형 정책 시나리오만 보여 준다. 예산 검토, 성과 확인 기준, 세부 실행 방법, 근거와 데이터 한계는 `POST /ai/v1/demo/11680/strategy-proposal.docx` Word 기획서에 정리한다.
- 이유: 담당자는 화면에서 빠르게 전략과 규모를 판단하고, 회의·결재용 상세 내용은 다운로드 문서로 검토할 수 있어야 한다.
- 주의: 시나리오의 방문객·관광소비액은 최근 월 실측값에 사용자가 입력한 목표율을 단순 환산한 값이다. ML 검증 전에는 정책 인과효과·매출 증가·관광객 증가 예측으로 주장하지 않는다. OpenAI는 구조화된 JSON 안에서 관측 사실과 제안을 구분하며, 예산 금액은 공식 단가 근거가 없으면 만들지 않는다.

### D-015 독립 기획 추천안과 실행 비교 시뮬레이션

- 상태: D-019로 대체됨
- 결정: AI 전략은 `1개월 단기 전략`·`3개월 단기 전략`·`1년 장기 전략`의 독립 기획 추천안 3개로 표시한다. 각 추천안에는 구체적 실행 설명과 2~3개 착수 항목을 함께 제공하며, 선택한 추천안은 오른쪽 시뮬레이션과 연결한다.
- 이유: 담당자가 시간 순서의 파이프라인이 아닌, 예산·여건에 맞춰 검토할 수 있는 서로 다른 실행 대안을 빠르게 비교하도록 하기 위함이다.
- 주의: `전략 미실행`과 `전략 실행 목표` 비교는 담당자가 조절한 방문객·관광소비 목표율을 최근 월 실측값에 단순 환산한 것이다. 이는 AI·ML 예측이나 정책 인과효과가 아니다. 유사 지역 비교는 검증된 공통 지역·기간 원자료가 확보된 뒤에만 AI 근거로 사용한다.

### D-016 실행 산출물 중심 AI 기획안

- 상태: 승인됨
- 결정: AI 전략의 각 항목은 해결할 데이터 문제, 실행 설명, 2~3개 작업과 산출물, 기대 변화, 확인 지표, 근거를 구조화해 생성한다. 화면과 문서에서는 역할 호칭 대신 기획안 자체를 표시한다.
- 이유: 수치 근거 없이 "강화"·"활성화"만 반복하는 일반론을 줄이고, 실행 후 무엇을 검토할 수 있는지 명확히 하기 위함이다.
- 주의: 현재 AI 입력은 강남구 원본 ZIP에서 계산한 snapshot과 최신 소비 업종대분류다. 공식 정책·교통·관광자원 문서를 수집·출처 등록하기 전에는 RAG나 유사 지역 사례를 실제 보고서 근거로 사용하지 않는다.

### D-017 지역 원본 공통 대시보드·전략 보고서

- 상태: 승인됨
- 결정: `data/raw/{시도}/{시군구}`에 있는 공식 원본에서 방문자·외지인 관광소비·숙박/체류·내비게이션·SNS 표가 검증된 지역은 하나의 AI 대시보드·전략 보고서 경로로 처리한다. 최초 지원 지역은 서울특별시 강남구, 인천광역시 계양구·서구·옹진군이다.
- 이유: 지역별 파일명이 연도·다운로드 시점에 따라 달라도 표 이름을 기준으로 실제 원본을 읽어, 신규 지역을 같은 사용자 흐름에 추가하기 위해서다.
- 주의: 현재 전략 근거는 해당 지역의 관광데이터랩 원본 관측값과 OpenAI 구조화 출력이다. RAG, ML 예측, 외부 관광 Open API를 추가했다는 뜻이 아니며, 새 지역은 원본 표·지역명·지역 코드 검증 뒤에만 지원한다.

### D-018 시도 내 시군구 최근 3개월 비교

- 상태: 승인됨
- 결정: 시도를 선택하면 `data/raw/{시도}/{시군구}`에 실제 원본이 있는 시군구만 대상으로, 공통 최근 3개월의 순 방문자 수와 외지인 관광소비액 평균을 비교 차트에 표시한다.
- 이유: 선택 지역의 규모를 같은 기간·같은 집계 기준으로 간결하게 비교하기 위해서다.
- 주의: 현재 인천광역시는 계양구·서구·옹진군 원본만 있으므로, 다른 군·구의 수치를 추정하거나 표시하지 않는다. 원본을 추가하면 같은 계산으로 자동 포함한다.

### D-019 단일 3~6개월 관광 기획안

- 상태: 승인됨
- 결정: 기존 `1개월`·`3개월`·`1년` 독립 추천안 3개를 폐기하고, 원칙적으로 향후 3~6개월 동안 방문자 수 또는 관광소비액 개선을 목표로 하는 단일 기획안을 생성한다. 화면과 Word 문서는 `문제 확인 → 솔루션 → 집행 방법` 순서로 동일하게 구성한다.
- 이유: 여러 선택지를 나열하는 것보다 선택 지역의 핵심 문제를 먼저 특정하고, 하나의 해결 방향을 일정·작업·산출물까지 연결하는 편이 실제 사업 검토에 유용하다.
- 비교 기준: 동일 시도의 `data/raw`에 원본이 있는 시군구만 공통 최근 3개월의 순 방문자 수·외지인 관광소비액·숙박 방문 비율·평균 숙박일수로 비교한다. 전국 또는 시도 전체 평균으로 표현하지 않는다.
- 예산 기준: 현재 원본에는 사업 단가와 견적이 없으므로 금액을 만들지 않는다. 비용 항목, 수량 기준, 공식 단가·비교견적 확보처, 계산식을 제시하고 견적 확보 후 확정한다. 실제 원화 범위는 근거 문서를 RAG에 연결한 뒤에만 계산한다.

### D-020 근거 수집·기획 작성·품질 검토 Multi-Agent

- 상태: D-030으로 확장됨
- 결정: AI 전략 보고서는 Evidence Agent, Planner Agent, Reviewer Agent의 고정 순서로 생성한다. Reviewer가 82점 미만 또는 critical 오류를 판단하면 Planner가 한 번 수정하고 최종 검토한다.
- 근거 범위: 정확한 수치는 데이터랩 원본, 관광자원은 허용 Open API, 공식 정책·사업 문서는 영속형 ChromaDB RAG와 허용 공식 도메인 조사만 사용한다.
- 이유: 자료 조사, 작성, 검토 책임을 분리해 일반론·근거 누락·장문 반복을 줄이고 실행 단계와 산출물을 강화하기 위해서다.
- 주의: Agent 수가 사실성을 보장하지 않는다. 출처가 없는 주장은 버리고, RAG 문서가 없으면 자료 공백을 표시한다. 재작성은 비용·지연을 통제하기 위해 최대 1회로 제한한다.
- 운영: Sol 기반 작성·검수는 오래 걸릴 수 있어 Agent 한 단계의 기본 대기시간은 300초로 두고 `AI_AGENT_TIMEOUT_SECONDS`로 조정한다.

### D-021 Agent 코드·프롬프트 분리

- 상태: 승인됨
- 결정: AI Server의 Agent 코드는 `ai_server/app/agents/`에서 Evidence·Case Scout·Transferability·Planner·Reviewer·Orchestrator 파일로 분리한다. 다섯 Agent의 프롬프트와 페르소나는 `agents/prompts.py` 한 파일에서 관리한다.
- 이유: 팀원이 Agent별 책임과 조정 위치를 쉽게 찾고, 한 Agent의 변경이 다른 Agent 역할과 섞이지 않게 하기 위해서다.
- 주의: 프롬프트를 조정해도 원자료 수치·출처·기간 규칙, 공식 도메인 제한, JSON Schema 검증은 완화하지 않는다.

### D-022 간결한 실행 기획안·목표 비교 시각화

- 상태: 승인됨
- 결정: AI 전략 팝업은 긴 본문 대신 `핵심 판단 → 문제·해결 방향 → 단계별 집행 → 실행/미실행 목표 비교` 순서로 표시한다. Word 기획서는 같은 내용을 도표·표 중심으로 최대 5쪽에 정리한다.
- 이유: 담당자가 읽기 전에 핵심 문제와 실행 방법, 검토할 목표 규모를 빠르게 판단할 수 있게 하기 위함이다.
- 주의: 목표 비교는 최근 월 원자료에 선택 목표율을 단순 환산한 검토값이다. 정책 인과효과·ML 예측·매출 증가 보장이 아니며, 1인당 소비는 집계 기준 검증 전에는 표시하지 않는다.

### D-023 계획 기간별 실행 목표 추이

- 상태: 승인됨
- 결정: 실행 목표 비교는 3개월 또는 6개월의 월별 방문자 수·관광소비액 추이를 표시하며, `미실행`과 `실행 목표` 선을 개별 또는 겹쳐서 검토할 수 있게 한다. 문제 확인, 솔루션, 집행 방법은 각각 독립된 화면 영역으로 표시한다.
- 이유: 목표 총액만 보는 것보다 계획 기간의 월별 변화와 실행 순서를 한 화면에서 검토하기 위함이다.
- 주의: 미실행 선은 최근 월 원자료 유지선이고 실행 선은 선택 목표율을 기간에 균등 배분한 검토선이다. 인과효과·정책 성과 예측이 아니다. 조사 공백은 Agent 내부 품질검토에 보관하며 팝업과 Word에는 긴 한계 문단을 표시하지 않는다.

### D-024 페이지별 프론트엔드 관리

- 상태: 승인됨

- 이유: 대시보드와 신규 기능을 한 파일에 섞지 않고 팀원별로 독립 개발하기 위함이다.

### D-025 쉬운 문장·근거 중심 5단계 기획안

- 상태: 승인됨
- 결정: AI 기획안은 쉬운 한국어로 `문제/제안 → 이 제안을 한 이유 → 해결 방법 → 5단계 실행 → 기대 변화` 순서로 작성한다. 판단 근거에는 실제 보유 기간의 월별 변화, 같은 기준의 지역 비교, 날짜가 확인된 공식 행사·정책 자료만 사용한다.
- 이유: 행정용어와 내부 역할 나열을 줄이고, 사용자가 왜 이 제안이 나왔으며 다음에 무엇을 해야 하는지 바로 이해하게 하기 위함이다.
- 표시 기준: 화면과 Word에는 내부 source_id·상세 KPI 문장을 노출하지 않고 `관광데이터랩`, `관광 Open API`, `공식 문서`와 자료명만 표시한다. Word에는 5단계 표와 프로젝트 타임라인을 함께 넣는다.
- 주의: 1년 자료를 3년 추세로 표현하거나, 행사 시점과 방문 변화가 확인되지 않은 상태에서 인과관계로 단정하지 않는다.

### D-026 근거 조사 병렬화·단기 캐시

- 상태: 승인됨
- 결정: Evidence Agent의 관광 Open API, ChromaDB RAG, 공식 웹 조사를 동시에 실행하고, Evidence Agent와 Case Scout Agent도 병렬로 실행한다. 동일 지역·동일 원자료·동일 조사 설정의 지역 근거는 기본 1시간, 공식 사례 근거는 기본 6시간 메모리에 재사용한다.
- 이유: Planner·Reviewer의 Sol 고추론과 품질 미달 시 1회 재작성은 유지하면서, 서로 의존하지 않는 외부 조회의 직렬 대기와 반복 조사를 줄이기 위해서다.
- 주의: 캐시는 기획안 완성본이 아니라 확인된 근거 묶음에만 적용한다. 원자료 또는 조사 설정이 바뀌면 캐시 키가 달라지며, 서버 재시작 시 사라진다. Planner 작성과 Reviewer 검수는 매번 새로 수행한다.

### D-027 전 지역 공통 최근 12개월 차트

- 상태: 승인됨
- 결정: 첫 대시보드와 AI 기획안의 방문자 수·관광소비액 월간 추세는 선택 지역의 가장 최근 12개월만 표시한다. 지원 지역을 바꿔도 카드·차트·관광소비 진단·지도 배치 구조는 동일하게 유지하고 값과 분석 내용만 바꾼다.
- 이유: 지역마다 1~3년 원본이 섞여 있어도 한 화면의 기간과 밀도를 같게 유지하고, 최근 변화가 3년치 축에 눌려 보이지 않게 하기 위해서다.
- 주의: 12개월보다 오래된 원본은 삭제하지 않는다. 향후 계절성 비교와 ML 시간순 검증에 사용하며, 현재 화면 응답에서만 제외한다.

- 주의: AI 전략기획서가 근거로 사용하는 동일 시도 원본 보유 지역 비교 계산은 유지한다. 화면에서 비교 그래프만 표시하지 않는다.

### D-029 API 크레딧 소진 시 오프라인 화면 테스트

### D-030 공식 성공사례 탐색·지역 적합성 평가 Agent

- 상태: 승인됨
- 결정: 기존 Evidence·Planner·Reviewer 흐름에 `Case Scout Agent`와 `Transferability Agent`를 추가한다. Case Scout는 공식 성과평가·결산서·예산서·보도자료에서 실제 관광사업의 대상, 운영 방식, 공개 예산, 관측 성과와 적용 조건을 수집한다. Transferability는 선택 지역 원자료와 사례 조건을 비교해 적합한 사례 1~3개와 3~6개월 시범사업 구조를 Planner에 전달한다.
- 사례 RAG: 검수한 공식 사례는 `data/rag/official_case_studies.jsonl`과 ChromaDB에 저장한다. 라이브 웹 검색은 최신 사례 보강용이며, URL과 기간이 없는 사례는 사용하지 않는다.
- 이유: `동선을 묶는다`, `홍보한다` 같은 일반론 대신 쿠폰·환급·숙박·행사·교통 결합 등 실제 집행 방식과 측정 가능한 중단·확대 기준이 있는 기획안을 만들기 위해서다.
- 주의: 타 지역에서 관측된 성과를 선택 지역의 보장 효과로 바꾸어 쓰지 않는다. 공식 평가가 인과효과를 검증하지 않았다면 참고 사례로만 표시하며, 예산은 공식 금액 또는 항목×수량×단가 산식으로만 제시한다.
- 표시: AI 팝업에는 근거 강도·제목·요약·원문 링크를 갖춘 공식 사례 카드를 최대 3건 보여 준다. Word 기획서는 일반 데이터 출처와 분리한 `참고한 공식 사례` 표로 정리한다.

### D-031 bid3 업무공간 디자인과 관광 AI 도우미 통합

- 상태: 승인됨
- 결정: TP2-3은 React + Vite, Backend FastAPI, AI FastAPI, MySQL 구조를 유지한다. bid3의 224px 사이드바, 64px 상단바, 1360px 콘텐츠 폭, 흰색 surface와 얇은 테두리 디자인을 관광 분석 화면에 이식한다. Django·SQLite·결제·입찰공고 기능은 가져오지 않는다.
- 지도: 메인 대시보드의 첫 분석 영역에서 가장 넓게 표시한다. 기존 VWorld 경계·Leaflet 선택 로직은 수정하지 않고 레이아웃 위치와 폭만 바꾼다.
- 챗봇: 선택 지역 원자료 snapshot, 현재 구조화 기획안, 허용된 공식 웹 자료를 입력으로 사용한다. `설명`, `공식 사례 조사`, `기획안 수정안 제안`을 지원하며 수정안은 자동 저장하지 않고 사용자가 적용해야 한다.
- 출력: 화면은 그래프·카드·지도 중심으로 유지하고, AI 문장은 짧고 쉬운 한국어로 제한한다. 기획서의 사실 수치와 예측·제안은 계속 분리한다.
- 이유: bid3의 균형 잡힌 업무공간 UX를 재사용하면서 TP2의 데이터·ML·RAG·5-Agent 전문성을 잃지 않기 위해서다.

### D-032 TP2-3 개발 포트 분리와 반응형 소개 화면

- 상태: 승인됨
- 결정: TP2-2와 동시에 실행할 수 있도록 TP2-3의 로컬 개발 실행은 Backend `8100`, AI Server `8111`, Frontend `5176`을 사용한다. Windows에서 `8101`이 예약되어 AI 서버가 시작하지 않는 환경과 다른 프로그램이 `5175`를 점유한 환경을 피하기 위한 변경이다. 배포 시에는 기존 Nginx `/`, `/api`, `/ai` 구조를 유지한다.

### D-033 실제 데이터 안전 표시와 로딩 성능 개선

- 상태: 승인됨
- 결정: `/`와 `/dashboard`는 React 지연 로딩으로 분리한다. 원본 ZIP·CSV 파싱은 `ai_server/app/raw_data_repository.py` 한 곳에서 담당하고, 상대경로·크기·수정시각 지문이 같은 동안만 LRU 캐시를 재사용한다. Backend·AI Server의 큰 JSON 응답에는 GZip을 적용한다. 키를 제거한 VWorld GeoJSON은 지도 표시용으로 단순화해 24시간 로컬 디스크 캐시를 재사용하고, 브라우저에는 선택 시도의 시군구만 반환한다.
- 표시 기준: 지원 지역의 FastAPI 응답이 성공한 경우에만 실제 수치를 표시한다. 미지원·오류 지역은 개발용 예시 숫자로 대체하지 않고 빈 상태와 원자료 연결 안내를 표시한다.
- 이유: 첫 화면의 JavaScript 전송량, 반복 ZIP 파싱, 전국 경계 전송량을 줄이면서 데이터 출처가 불명확한 숫자가 실제 값처럼 보이는 문제를 방지하기 위해서다.
- 주의: 이 개선은 MySQL 적재나 ML 예측 완료를 뜻하지 않는다. 현재 구현·부분 구현·미구현 범위와 측정값은 `docs/PROJECT_AUDIT.md`에서 관리한다.

### D-092 PDF 청크 보존과 지표 정의 누락 공개 (2026-09-07)

- 발견: 페이지별 PDF 청크는 RAG 수집 단계에서 보존했지만, 기획 Orchestrator와 로컬 근거 도구가 `source_id`만으로 합쳐 같은 문서의 다른 페이지를 덮어쓸 수 있었다. 따라서 검색 결과 5개가 있어도 작성 Agent에 1개만 전달될 위험이 있었다.
- 변경: 병합 키를 `(source_id, chunk_id)`로 통일하고, 로컬 Agent는 같은 문서의 페이지 청크를 `offset` 순서로 읽어야 해당 문서를 읽은 것으로 표시한다. Chroma 의미 검색도 chunk ID·쪽수·원문 전체를 보존한다. PDF의 원문 `source_id`는 인용 ID로 그대로 유지한다.
- 데이터 정의: `get_region_metrics`는 공식 관측값과 함께 업종별 관광소비 구성을 전달한다. 업종 비중은 원인·사업 효과·개별 방문객 객단가의 증거가 아니라는 해석 한계를 함께 고정한다.
- PDF 확인: 지방공항 자료 34~44쪽은 추출 가능했다. 데이터 세미나 75~99쪽은 대부분 이미지/특수 폰트라 텍스트 추출에 실패했다. 화면으로 직접 확인한 76쪽만 검수 요약으로 RAG에 넣고, 나머지 누락 쪽수는 재생성 CLI가 경고한다. 따라서 이 PDF 전체가 RAG에 색인됐다고 주장하지 않는다.
- 검증: PDF 3페이지가 합치기·재작성·로컬 페이지 조회를 모두 통과하는 회귀 테스트, RAG 청크 메타데이터 보존, 미래 월 변조가 과거 ML feature 행을 바꾸지 않는 검사, 기존 계획·ML·PPT 검증을 포함한 선택 회귀 171개를 통과했다. 유료 OpenAI·임베딩·재학습은 호출하지 않았다.
